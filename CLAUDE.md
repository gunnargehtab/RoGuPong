# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

RoGuPong is a 16-bit-styled pong duel for two phones on the same WiFi — or, online, on any two networks. There is no game server: the two browsers connect directly over WebRTC, exchanging the handshake by QR code (online, by pasting codes through a chat app). It is plain static files — no build step, no package.json, no framework, no third-party libraries, and no binary assets. The pixel font, logotype, QR encoder, audio and stages are all generated in code at runtime.

**Keep it that way.** The zero-dependency, everything-generated constraint is deliberate: it is what lets the game run from the service-worker cache on a WiFi network with no internet behind it. Do not add npm packages, CDN scripts, image/audio files or web fonts.

The project's one server is optional: a Cloudflare Worker in `cloud/` that syncs leaderboard leagues (see *Cloud league sync* below). It holds finished matches only, never anything a live match waits on. The game must keep working fully without it — offline, with the Worker down, or with none deployed — and it stays dependency-free itself: plain JS, deployed with `npx wrangler deploy` (`cloud/README.md`), and not part of the game's files or `sw.js`.

## Running it

```sh
python3 -m http.server 8137     # any static server works
```

Open `http://localhost:8137`. There are no tests, linters or build commands in the repo — verification is playing it. Camera access (QR scanning) requires HTTPS or `localhost`; over plain http on a phone, use the copy-and-paste code fallback that every connect screen offers.

`window.rogupong` is the live `App` instance in the console — the easiest way to poke at a running match (e.g. `rogupong.match`, `rogupong.peer`).

Deployment is GitHub Pages serving straight from `main`; every push to `main` republishes.

## Architecture

`js/main.js` defines `App`, the conductor: screen router (`go()`), connection lifecycle, and the frame loop. Menus are DOM (`js/ui/screens.js`) layered over a single full-screen canvas that renders both the menu backdrop and the match (`js/game/render.js`).

**Court model.** The match simulation (`js/game/match.js`) runs in a normalised court: x and y both 0..1, player 0 defends the bottom, player 1 the top. The renderer flips y for player 1, so each phone shows its own player at the bottom. `App.view` (0 host, 1 guest) is the local player index. The court is `COURT_ASPECT` (0.56, exported from `match.js`) as wide as it is tall, so anything round in court space — the SPIRE's collision circle — is computed in aspect-corrected coordinates. Court and HUD are laid out inside the screen's safe area (`Renderer.safe`, read from `env(safe-area-inset-*)` on every resize), so a notch or home indicator only covers backdrop. HUD text is sized from those strips and the court's width (`Renderer.hudLayout`), never the screen's width, and stays within the court's edges. There is no special button: the special fires on a quick tap in your own paddle's column (`js/game/input.js`, tested against `Renderer.myPaddle`, the paddle as last drawn), and the paddle itself shows the meter as a strip that fills and then blinks.

**Netcode: host-authoritative, guest predicts only its own paddle.** The host runs the full simulation at a fixed 1/60 timestep (accumulator in `App.stepMatch`) and broadcasts snapshots at 30 Hz. The guest sends only its paddle x at 30 Hz, extrapolates ball motion between snapshots, and simulates its own paddle locally (`App.predictPaddle`), reconciling against the span its paddle covered in the last 0.45 s (`App.predictMemory`: the round trip + 0.2 s when that is longer) — the authoritative echo is ~a network round stale, so only divergence beyond that recent span counts as desync (eased away, or snapped past 0.14 court). Lag is made up for in half round trips (`App.halfTrip`, from the heartbeat's smoothed `Peer.rttAvg`, capped at 0.1 s): the guest draws each snapshot's balls that far ahead (`Match.project`), bouncing them off the side walls between snapshots too but never drawing one through a paddle face (`toFace` — whether it is returned there is the host's call), and the host lets the guest's paddle save a ball up to that long after it crossed the face (`Match.grace`, `Match.inGrace`; the goal waits too). None of it changes the wire format. Two data channels ride one `RTCPeerConnection` (`js/net/peer.js`):

- `ctl` — reliable + ordered: lobby messages, character picks, special presses, match start/result, emotes. Handled in `App.onMessage` (typed `{t: ...}` messages).
- `state` — unreliable + unordered: 30 Hz snapshots and paddle inputs, discarded if older than the last applied tick. Handled in `App.onState`.

Anything that must not be lost goes on `ctl`; anything superseded by the next packet goes on `state`. The full `ctl` vocabulary is the switch in `App.onMessage`: `hello` (protocol version `v`, name, character, the newest 80 matches, `more`: how many follow, and `league`: the cloud league key this phone syncs with, if any), `hist` (the rest of the history, 40 matches a chunk, `end` on the last — sent through `Peer.sendPaced` so it never blocks lobby messages), `setup`, `pick`, `ready`, `start`, `sp` (guest special press), `result`, `rematch`, `emote` (`i`, an index into `EMOTES` in `screens.js`: eight emoji, then quick-chat lines from `QUICK_CHAT_FROM` — append only; an unknown index pops a 👋), `away` (this page hid or came back, `v` true/false — holds a match when both phones speak `PAUSE_SINCE`, and feeds the diagnostics; builds from before it never send it), `bye` (also sent on `pagehide`, so a closed tab is noticed at once; `why: 'away'` and `p`, the player who was away, when a match is called off). `ping`/`pong` never reach `App` — `peer.js` consumes them to measure `peer.rtt` and as a heartbeat (every 1.5 s). How long silence is tolerated is `Peer.patience`, which `App.linkPatience` sets: 8 s in a match, 30 s anywhere else, 35 s while a paused match waits for the friend. A hidden page passes no verdicts, nor for two heartbeats after it comes back (`Peer.backOnScreen`). A link WebRTC reports `disconnected` gets at least 10 s to recover first (`Peer.startGrace`), or the patience if that is longer. Every drop goes through `App.onDrop`, which records the reason, the step, how long the line was quiet and whether either page was hidden (`App.describeDrop`). A handshake that never opened lands on the `lost` screen titled COULDN'T CONNECT with Try again (`next: 'retry'` → `App.retryHandshake`, the same side over in the same mode). A link that was up and drops unasked goes straight back into the handshake on the same side (`App.beginRejoin`; `App.role` survives the drop, and the stage, rules and picks were never reset), with a Reconnecting banner (`App.rejoin`, `Screens.rejoinPanel`). A `bye` or a called-off match lands on Link Lost with a Reconnect button. `App.watchHandshake` ticks the handshake screens' status line in place, reveals their "taking a while" block (`hs-later`) and gives up on connecting past `CONNECT_TIMES`.

**Mid-match pause.** When either page hides mid-match, both phones hold the match (`App.updateHold` → `Match.hold`). Everything but the paddles freezes. The phone still on screen shows the `paused` screen over the frozen court. When both phones are back, a 3 s resume countdown runs (`Match.resume`). The host's hold rides the snapshot as `pa`. A guest holds its own copy meanwhile, and ignores snapshots while the host is away. A match waits `AWAY_LIMIT` (30 s) for a phone that left, then either phone calls it off (`App.callOff`). It needs `PAUSE_SINCE` (protocol 4) on both phones; against an older build nothing holds. The wake lock is held whenever `App.peer` exists (handshake through results) and re-requested each time the page comes back (`App.keepAwake`, `App.onVisibility`).

**Signalling is optical.** `js/net/sdp.js` compresses a ~1.2 KB SDP offer to a ~117-char code by extracting only what differs between ends (ICE credentials, DTLS fingerprint, candidates), packing binary and Base32-encoding — prefix `RGP`. If the compact round-trip self-check fails it falls back to deflate-compressed full SDP, prefix `RGX`. `js/net/qr.js` is a complete from-scratch QR encoder; `js/net/scanner.js` scans via the Barcode Detection API (Chromium-only). ICE gathering is treated as settled 0.4 s after the last candidate (3 s hard cap) so internet-less networks don't stall. While the host's invite is on screen its camera is already scanning for the guest's reply, so the second scan needs no tap; codes can also be shared as text (Web Share API) and auto-connect when pasted.

**Online play** (the connect screen's Online tab, `App.online`). Same handshake, codes through a chat app, no camera; no TURN relay, so some network pairs simply can't connect and are told so. An online code (`packSignal(…, { online: true })`) puts `srflx` candidates first and carries a 5-byte trailer after the candidates — flags, then the Unix time in seconds — which older builds never read that far to see (the `RGX` fallback carries it as an `a=x-rogupong-online` line). An online invite without an internet address throws `err.code 'no-internet'` (the NO INTERNET screen). Gathering waits for a STUN answer (8 s cap). Opening an online invite makes the guest online too (`Peer.join` → `peer.online`, `peer.inviteAt`). Before it opens, an online `Peer` ignores `failed`: the guest's checks give up ~15 s after it makes the reply, but the host's first check once it has the reply still brings the link up (tested in Chrome); `App.watchHandshake` does the giving up. Re-adding candidates can't restart checks — Chrome ignores remote candidates it has seen. An iPhone stops a page off screen, WebRTC included, so an online guest has to be back from the chat app to answer the host's checks: the reply screen says so (and again on return), and time a page spends hidden doesn't count against `CONNECT_TIMES`. The host's online invite screen holds the reply paste box, and coming back to it lights up Paste (`App.offerPaste`, which reads the clipboard itself where the permission is already granted). Online, music plays ducked (`audio.setDucked`) for a call running alongside.

**iPhone path.** iOS browsers cannot scan QR codes, so the host's invite is encoded as a URL (`…/#j=<code>`) that the iPhone's own Camera app reads. `App.consumeInviteLink` handles it on startup *and* on `hashchange` (tapping an invite while the page is open only changes the fragment). The reply code stays bare, scanned inside the game by the host. A Camera-app invite always opens in Safari (or the default browser), never in a home-screen copy with its own storage; the join screen says so on iPhones (`isIOS()` in `js/diag.js`), and on iOS the game asks for persistent storage (`App.keepStorage`). A link skips the connect screen and its name box, so the guest's reply screen asks for a name while it is a stand-in. An invite opened in a chat app's own browser (`inAppBrowser()` in `diag.js`: no `Safari/` token on iOS, `wv` on Android) keeps its `#j=` fragment until the link opens, so the app's Open in Safari carries it, and the online screens say to go there first. On iOS the game paints `icon.svg` into an `apple-touch-icon` at startup (`addTouchIcon`), since iOS ignores SVG icons.

**Leaderboard** (`js/data/leaderboard.js`), with no server needed: each phone keeps immutable match records with random ids in `localStorage` (up to `MAX_RECORDS`, 3000, parsed once and cached in memory); on connect, phones exchange their *whole* history — matches between other friends included, so a group converges on one league — and take the union (`mergeMatches`, which also weeds out malformed records). Host and guest build identical records from the shared match id (`App.buildRecord`), which is what makes the merge conflict-free; records carry the host's `balance` version and the `party` flag. Everything shown — standings, head-to-head, per-hero stats (`heroStats`, `heroVerdict`), cosmetic flair unlocks (`FLAIRS`/`flairProgress`) — is *computed* from those records at read time, never stored — keep it that way when adding milestones or stats. `js/data/league.js` moves history in and out by hand: league codes (`RGL` prefix, deflated JSON in Base32, for Share/Import league) and the Copy history CSV (names anonymised unless asked).

**Cloud league sync** (optional; `js/data/cloud.js` on the phone, `cloud/worker.js` on Cloudflare). A league is a random 16-character Base32 key with no accounts behind it; it rides in `hello` and inside league codes (`k`), and a phone in no league joins the first one it sees (`App.cloudSeen`) — one already in a league, or whose player left (`off`), only gets it offered on the leaderboard (`App.cloudOffer`). Each league is one SQLite Durable Object: records keyed by match id, rows numbered in arrival order. A phone keeps a cursor (last row fetched) and an outbox of ids that reached it other than from the cloud — `mergeMatches(recs, from)` and `recordMatch` announce new ids through `lb.onNewMatches`, and anything not `from === 'cloud'` is queued. `syncLeague` pages 500 up and 500 down per request, merges what arrived once at the end and only then moves the cursor; a cursor past the league's end gets `reset` and the phone sends everything again. `App.requestSync` is the single trigger (startup, new matches, leaderboard open, page back after 10 min, network back), never runs mid-match, and backs off from 30 s to 10 min after failures. The feature is invisible when `ENDPOINT` in `cloud.js` is empty (a `rogupong.cloud.endpoint` value in `localStorage` overrides it for testing). The game's own history stays the source of truth; the cloud only ever adds through the same merge.

**Stages are scene modules** (`js/game/scenes/<id>.js`, helpers in `scenes/kit.js`). Each paints a side-on backdrop and a top-down court floor in *art pixels* — a canvas `ap` (≈ min(W,H)/180, at least 2) times smaller than the screen — which the renderer caches per stage and size and scales up nearest-neighbour (`Renderer.sceneLayer`), plus optional `animateBackdrop`/`animateCourt` hooks that run on full graphics only. Scene painting is deterministic (seeded `mulberry`, never `Math.random`) and uses flat colours with banding/dithering, never smooth gradients, shadows or filters. Court floors must stay dark and low-contrast (the ball and paddles have to pop) and vertically symmetric (each phone sees the court from its own goal — `kit.mirrorY`). A scene owns its palette (`accent`, `court`, `line`); `stages.js` owns names, blurbs and each stage's crate pool, which `App.startMatch` hands to `Match` as `opts.items`.

**Performance.** `App.sampleFrameRate` watches the real frame rate and drops `renderer`/`fx` to a `low` quality path for the rest of the session if the phone can't hold ~45 fps — windows close on 45 frames or 1.5 s, whichever comes first, one window under 27 fps demotes immediately, and a steady ~30 fps (an OS frame cap such as iOS Low Power Mode) never counts as slow. The automatic switch is never saved: `App.quality` is the session's level, while `profile.quality` holds only a choice made on the Graphics toggle (marked `qualityChosen`), which also pins it for the session. Both levels blit the cached stage art rather than repainting it; `low` renders at 1× DPR and skips the scenes' animation layers, canvas shadows and the CRT pass; gradients are cached by key in both quality levels (`Renderer.grad`). DESIGN.md §9 explains the budget-phone rationale.

## Things to know when editing

- **`sw.js` precache list**: every file the game loads must be listed in `ASSETS`, so adding or renaming a JS/CSS file means updating `sw.js` too. Fetch is network-first with cache fallback, so redeploys are picked up automatically.
- **DESIGN.md is the source of truth for tuning.** Every physics constant (paddle speed 2.35, speed ramp ×1.035, rally-pressure shrink, meter rates…) was deliberately balanced — the file explains why each number is what it is. Read the relevant section before changing gameplay values, and keep the doc in sync with the code.
- **`PROTOCOL` in `main.js`** is what this build speaks, exchanged in `hello`. Bump it whenever a change needs both phones on the same build to look right (new snapshot fields a guest must draw, new crates), and tag new crates with `since: <that number>` in `items.js` — a match against an older build leaves them out of the pool (`App.stageCrates`), and the lobby tells the players which phone to update.
- **`BALANCE` in `characters.js`** is the roster's balance version, saved in every match record so the Heroes tab can show win rates since the last patch. Bump it with any change that could shift who wins — a hero's numbers, or how a special plays out in `match.js` — usually alongside the `PROTOCOL` bump such a change needs, and note it in DESIGN.md §3.
- **Stage objects** raised by the signature crates (SPIRE's pinnacle, AVALANCHE's snowdrift) and by GU's second AEGIS press (the midline `wall`, only when both phones speak `MIDLINE_SINCE`) live in `Match.props`, ride the snapshot as `pr`, and are bounced off guest-side in `extrapolate()` too. New snapshot fields are always appended to the end of their arrays so a phone on an older build ignores them.
- **Every free ball keeps heading for a goal** (`Match.keepHeading`, `MIN_VY`), and a flat one travels faster than its `speed` (`Match.lean`). The floor runs every step, and also right where a new heading is set (a return, multiball, QUAKE), so no snapshot shows a ball below it. Anything that needs how fast a ball really moves must use `speed × lean`; the snapshot already sends the leaned velocity.
- **Matches are set up entirely by the host's `start` message** (`App.hostStart`): seed, stage, target, party flag, characters, match id, balance version — both phones construct their `Match` from it. Inside the simulation all randomness goes through the seeded PRNG (`this.rand`, mulberry32), never `Math.random`, so serves and crate rolls stay tied to the shared seed.
- **Diagnostics** (`js/diag.js`): a 60-entry event log kept in `sessionStorage` (so it survives the reload iOS does after discarding a background tab), plus `App.diagnostics()`, the report the Copy diagnostics button copies from the title and Link Lost screens. When touching anything that can fail on a phone — the link, audio, the wake lock, visibility, cloud sync — `log()` its moments. Keep entries rare (each is a storage write) and free of player names and cloud league keys, since reports get pasted into public issues — the report's last-drop line uses the drop's name-free `plain` text for the same reason.
- **The cloud Worker and `cloud.js` share a wire format** (`POST /league/<key>`: `{since, recs}` → `{recs, cursor, last, more, reset}`, 500 a page — `cloud/README.md`). Change them together, and keep the Worker answering older phones: a deployed Worker serves every build still cached on a phone.
- Both `README.md` and `DESIGN.md` describe behavior in detail; user-visible changes usually need a matching edit there.
- In-game text renders through the 62-glyph 5×7 bitmap font in `js/ui/pixelfont.js`; new glyphs must be added there before they can appear on the canvas.
